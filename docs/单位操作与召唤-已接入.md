## 一、RVA / 结构偏移总表

以下地址与偏移基于 CE 修改器，并对本机 `ra3_1.12.game` 逐字节验证（含每个功能 hook 点的
原始指令 + cave 内动作）。游戏 ImageBase `0x400000`。

| 名称 | RVA | 说明 |
|---|---|---|
| 玩家管理器 | `0x8E08DC` | 全局指针 → mgr；`mgr+0x50` = 选中链表头，`mgr+0x5c` = 选中数量 |
| 对象模板库 | `0x8E6C58` | 全局指针 → store |
| 当前对象哈希 | `0x8E9838` | 当前操作对象的类型哈希 |
| 光标坐标 | `0x8DAEFC` | 全局指针 → 坐标对象；`+0x3c`=x `+0x40`=y `+0x44`=z |
| 模板查找 | `0x3E4230` | `__thiscall(this=store, hash)` → `template*` |
| **创建单位** | `0x2440F0` | `cdecl(0, template, float* pos, team, team+0x10)` → `object*` |
| 屏幕像素 → 世界坐标 | `0x1ED4A0` | `cdecl(void* src, void* dst, int, int)`；`src` = 客户区像素 (x, y, 上下文) 三个 dword，输出该像素射线命中的**地形表面世界坐标（含高度）**。第三参数不参与运算 |
| 出厂等级(基)车) | `0x35C200` / `0x39EA50` | 备用 |

**单位结构偏移**（相对 `obj` 与 `body`）：
| 字段 | 位置 |
|---|---|
| body | `[obj+0x138]` |
| 血量体 | `[body+0x33c]`；`+4`=当前, `+0xc`=上限, `+0x10`=备份 |
| 归属玩家对象 | `[body+0x418]` |
| 速度链 | `[body+0x374]` → `[+0x200]` → 子节点数组；节点 `+8`=速度（第二节点还需 `[+0x18]==1.0f`）。原速备份由修改器自己记账（节点地址 → 原速），不用 CE 那套 `+0x40` 槽 |

**链表遍历**：`node = [mgr+0x50]`；`obj = [node+8]`；`node = [node]`；共 `[mgr+0x5c]` 次。

## 二、已实现的功能

| 功能 | 实现 |
|---|---|
| **移速（单位面板滑条）** | 遍历选中单位 → 速度链节点 `+8` 写入滑条值（`0` = 定住，量程 `0..1000`；松手/回车才写入）。改前把原速记进修改器自持的备份表（键 = 节点地址），「恢复原速」写回该值 |
| **超速 / 慢速 / 定住 / 恢复（对战面板 + 热键）** | 同一套读写路径，档位值 `500 / 10 / 0`，恢复走同一个备份表 |
| **无敌 / 残血 / 恢复血量** | 血量体 `+4`(和 `+0xc`) 设 `999999 / 1.0`；恢复=`+0x10` → `+4,+0xc` |
| **收编敌方（复制到己方）** | 选中单位 `[body+0x418] = 本地玩家对象`；若"当前对象哈希"是 6 个超武之一则跳过（基于 CE） |
| **摧毁选中** | 调 `KillUnit`（RVA `0x39EA50`，`ecx=Thing`，栈参 `(6,19,0)`）。⚠️ 别在游戏流程**之外**直接写血量 0 —— 会留下「幽灵单位」（对象不回收、模型仍在）；「秒杀」hook 因在流程**内**改写，不受此限 |
| **召唤单位（支援代码/哈希）** | `FindTemplate(hash)` → `CreateUnit(0, tmpl, pos, 本地玩家, [玩家+0x10])` × N |
| **召唤基地车** | 同上，用 3 个 MCV 哈希（`0x28DA574E / 0xAF4C0DA5 / 0x1C2EF767`） |
| **空投箱** | 同上，箱子哈希取自 `units_corona.h` 的 `kCrates[]`（54 种） |
| **单位状态（铁幕 / 无敌 / 加速 / 减速 / 易碎 / 输出增强 / 重置）** | **表驱动**（`actions.cpp` 的 `kUnitStatus[]` + `ActUnitStatus`）：每个状态 = 若干引擎 modifier（`0x7181F0` 施加 / `0x718300` 解除）+ 若干 ObjectStatus（`Object::SetStatus`）+ 可选定身/易碎联动；「重置」= 撤全部 modifier + 速度还原 + 血量回满。UI：单位面板「单位状态」组（下拉 + 施加/解除/重置）；HTTP：`/status`。**不写引擎槽位内部字段**（见 §九.6） |

落点三来源（按 UI「落点来源」设置排序，默认**视野中心**优先；也可用 `/summon?place=` 单次点名，
或用 `?x=&y=&z=` 直接指定坐标）：

| 来源 | 取法 | 可靠性 |
|---|---|---|
| **视野中心** | 游戏客户区**正中的像素** → 换算函数 `0x1ED4A0` → 命中的地面世界坐标 | 稳。不依赖相机矩阵，也不依赖鼠标；窗口失焦照样对 |
| **选中单位** | 首个选中单位 `body+0x38/+0x3c/+0x40` | 稳。前提是有选中 |
| **游戏光标** | `[0x8DAEFC]` 对象 `+0x3c/+0x40/+0x44` → 同一个换算函数 | ⚠️ **只在鼠标位于游戏窗口内时刷新**。玩家切出去（例如与 AI 对话）时它停在旧值 → 投到"上次鼠标停留处"，那个点在水面就落海 |

> **为什么不用 d3d9 相机矩阵反投影**：实测游戏 `SetTransform(D3DTS_VIEW)` 传的全是单位矩阵
> （34530 次调用、`_33` 恒为 1.0），3D 相机根本不走那条通道 —— 反投影此路不通。

## 五、风险与后续

- 这些是**直接改游戏内存 + 调游戏函数**，全部用 SEH 包裹 + 空指针校验；但**参数契约若与游戏版本不符仍可能崩**。
  所有动作都是**用户手动触发**，不会自动跑。
- **未实现**（尚未接入）：
  `协议无冷却 / 单位技能无冷却 / 禁用敌方协议 / 弹药无限(*) / 满级 / 一键满状态 / 混乱模式 /
   刷矿车车队 / 出场等级 / 单位属性检视`
  （`*` 弹药无限其实已有 FLAGS+0x12 hook）
- **按名字召唤**：运行时扫模板库找哈希 → 可解锁任意对象（含基础版 `UnitCrate`）。

## 六、实测定位

**渲染完全正常**（菜单画在游戏里、8995 帧、16/16 hook 安装）。后端失败，用内存探针定位到：

| 检查项 | 实测值 | 结论 |
|---|---|---|
| 模块基址 | `0x400000`（`RA3_1.12.game`，无 ASLR） | ✅ |
| `g_localPlayerId` / `g_localPlayerObj` | `2` / `0x319e6a0` | ✅ **玩家已抓到**（界面显示"未抓到"是旧构建/时序问题） |
| 功能 hook | `total=16 installed=16 aobOk=16` | ✅ |
| `[base+0x8E6C58]` ThingFactory | `0x3473c58`，`[+0]=0x00c61518`(vtable)，紧邻字符串 **"TheThingFactory"** | ✅ 真是对象工厂 |
| `Find`(0x3E4230) | 在 `0x4dff8d` 处实锤：`mov ecx,[ThingFactory]; call 0x7E4230`（与解析结果一致） | ✅ **模板查找可用** |
| `[base+0x8E08DC]` 选中管理器 | `0`（当时无选中） | ⚠️ 需先选中单位 |
| **`CreateUnit`(0x2440F0)** | 运行内存与文件一致，但**该地址落在指令中间**（真函数入口是 `0x6440C0`，0x6440F0 是 `mov [esp+0x10],edx` 的最后一个字节） | ❌ **地址与当前构建不符** |

→ 调用被 SEH 静默吞掉 = 日志显示"生成失败"但不崩。

**应对**：
- `LooksLikeFuncEntry()` 调用前校验目标首字节像不像函数入口；不像 → **不调用**，日志明确写"创建函数地址不匹配当前构建"
- `SummonLastError()`：精确报出失败环节（模板库空 / 模板未找到 / 玩家为0 / 玩家+0x10空 / 落点取不到 / 地址不匹配 / 调用异常 / 返回空）
- 「设置 → 诊断」的 **「诊断」按钮** → 一次性把上面所有值打进「输出记录」

## 七、地址表修正

基于 CE 的地址表（针对 1.12.3444.25830），其 18 处偏移已对本机 `Data\ra3_1.12.game` 逐字节验证。
原表有三个 RVA 与本机构建不符，修正后实测可用：

| 项 | 原值（❌ 对本构建） | **修正后（✅ 实测可用）** |
|---|---|---|
| 创建单位 | `0x2440F0`（落在指令中间） | **`0x205240`** — `cdecl(0, tmpl, float* pos, team, team+0x10)`（干净函数入口，`8b4c2408 83ec3c 53`） |
| 选中管理器 | `0x8E08DC`（恒为 0） | **`0x8DB73C`** — `+0x50` 链表头 / `+0x5c` 数量（实测 `[0x8DB73C]=0x36209b0, +0x5c=1` ✅） |
| 光标坐标 | `0x8DAEFC`（指向全零对象） | 仍然用它拿"鼠标处世界坐标"，但要知道它**只在鼠标位于游戏窗口内时刷新**（见 §二 落点三来源） |

**其它可用项**（均实测为干净入口）：
| 功能 | RVA | 调用 |
|---|---|---|
| 单位升级（满级） | `0x35C200` | `ecx=unit, cdecl(3, 1, 0)` |
| 击杀选中 | `0x39EA50` | `ecx=unit, cdecl(6, 19, 0)` |
| 模板查找 | `0x3E4230` | `ecx=[0x8E6C58], arg=hash` |
| 屏幕像素 → 世界坐标 | `0x1ED4A0` | `cdecl(src, dst, 0, 0)`；src=(像素x,像素y,上下文) |
| **免费建造** | **`0x0E7565`** | 字节 `75 0C`(jne) → **`EB 0C`**(jmp)，建造检测恒真 |

### 两个实现要点
1. **迷雾去除**：`MapCaveStub` 必须**先重放原指令 `movss [ebp+0x260],xmm0`、再覆盖**为 `100000` ——
   反序会被原指令冲掉。
2. **快速建造**：`FastBuild3CaveStub` **不碰 `[esi+0x1bc]`**（那是别的计时器），只做 `[edi+0x14] = [edi+0x3c] + 1`
   （且 `ebp==1` 时跳过），建造队列才保持一致。不想用快建时可用更安全的**免费建造**（1 字节补丁）。

## 八、版本兼容：符号解析器（AOB + 结构推导）

> CE 表只对 1.12 有效；此处改为"按字段 / 汇编反推"，以兼容其它版本与 mod。

**实现**：`src/symres.{h,cpp}`。解析顺序（每个符号独立）：

1. **特征码（AOB）全模块扫描** —— 唯一命中即用；
2. **多命中** → 取"离 1.12 已知 RVA 最近"的那个（版本小改时地址不会跑远）；
3. **0 命中** → 退回已知 RVA，但**必须通过函数入口形态校验**，否则标为解析失败（不盲调）。

**全局变量用结构推导，不靠固定地址**：

| 符号 | 依据 | 本机 1.12 实测 |
|---|---|---|
| ThingFactory 全局 | 先解析 `TmplFind`，再找 `8B 0D <imm32> E8 <rel32→TmplFind>` 的代码，取**出现次数最多**的 imm32 | **110 处代码一致**指向 `0xCE6C58` ✅ |
| 选中管理器全局 | 扫 .data：`[V+0x5c]∈1..64`、`[V+0x50]` 链表首对象及其 body 的 **vtable 都落在主模块内** | 仅 2 个候选，取最近的 = `0x8DB73C` ✅ |

**特征码唯一性（实测）**：`CreateUnit`(1) · `MouseMap`(1) · `LevelUp`(1, 20B) · `FreeBuildSite`(1, 20B) ·
`TmplFind`(2 → 用 ThingFactory 推导命中数判别真身) · `KillUnit`(3 → 就近)。

**自愈能力**：换版本后若 RVA 漂移，只要**特征码还在**（编译差异通常不改这些字节序列）就能重新定位；
`TmplFind` 这类同形函数用"结构关系"判别，比单看字节更稳。
每次启动把解析结果与来源写进「输出记录」（`[符号] 创建=... (AOB唯一) ...`），诊断页也会打印。

**残留硬编码**：`0xDAEFC(光标全局)` / `0x8E9838(当前对象哈希)` 仅作兜底与"超武跳过"判断，不参与主链路。

## 九、对象模型补充

### 1. Drawable 与 Thing 是两套指针，别混

| | 真实单位（Drawable） | 引擎对象（Thing） |
|---|---|---|
| vtable | `0x00BED890` | `0x00C4DB60` |
| 取对方 | `[drawable+0x138]` = Thing | —— |
| `+0x418` | **恒为 0** | = 归属 Team |

- **选中链拿到的是 Drawable**（`[[SelMgr]+0x50]` 链 → `node+8`）。
- **`CreateUnit` 返回的是 Thing**。
- **升级目标** = `[[obj+0x138]+0x3CC]`；**收编** = 把 `[Thing+0x418]` 写成本地 Team；
- **选中落点** = `[[SelMgr]+0x50]` 链 → `node+8`(Drawable) → `[d+0x138]` → `+0x38/0x3c/0x40`。

### 2. Thing 偏移速查

| 偏移 | 含义 |
|---|---|
| `+0x04` | 模板指针（模板 `+0x08` = 类型哈希） |
| `+0x33c` | 血量体（`+4` 当前 / `+0xc` 上限 / `+0x10` 备份） |
| `+0x418` | 归属 Team |
| `+0x374` | AIUpdate |
| `+0x38/0x3c/0x40` | 坐标 x/y/z |
| `+0xDC` | 对象 ID |
| `+0x80/0x84/0x88/0x90/0x94/0xD0` | 状态字（见下） |

### 3. 状态字决定护盾 / 技能回复

召唤、复制出来的单位如果状态字不对，会表现为"隐形"：小地图空心、敌方不攻击、反隐贴近才变实心。
正确写法（**创建后必须做后处理**，`actions.cpp` 的 `SummonByHash`）：

- 激活态：`{+0x80:0, +0x84:0x800, +0x88:0, +0x90:0x2, +0x94:0x20, +0xD0:0}`
- 隐形态（错误值）：`{+0xC8:0x800, +0x28:0x80000000, +0x208:0x80000000}` → 清成 `0` 即恢复
- ⚠️ `+0x90` / `+0x94` 会被引擎逐帧重算，所以**不能只在创建瞬间写一次**，要放在创建函数的后处理里。

> 根因分析全文：`docs/召唤单位状态字-根因与修复.md`。

#### 6.1 直调能做到的（🗑️ 历史 —— 视觉半已弃）

| 项 | 值 |

| `Drawable` | `[Thing + 0x0F4]`（vtable `0x00BED890`）；`Drawable + 0x138` 指回 Thing |

#### 6.2 差在哪（🗑️ 历史）

除外观（A 是"原模型+冰色调"、B 是"实心冰块模型"）外，两者字段**几乎完全一致**：

| 偏移 | A（直调） | B（真冻结） | 结论 |
|---|---|---|---|
| `Thing+0x090/0x094/0x098` | `00020002 / 00000220 / 00004000` | 同 | 一致 |
| `Drawable+0x188` 冰色 | 1.750 | 1.750 | 一致 |
| `Drawable+0x290` MC `PARALYZED`(379) | —— | `08000000` | **已排除**：给 A 补、或从 B 撤，画面都不变 |
| `Drawable+0x244/248/24C`（12B vector，1 元素） | 0 | 有 | **已排除**：把 B 的抄给 A，消融对比画面零变化 |
| MC `FROZEN`(428) | —— | **没有** | **已排除**：B 根本没这一位；A 用设置器置上也无效 |

⇒ 冰的"模型替换"既不是任何**模型条件**、也不是那三个**逻辑状态位**能触发的；
最可能是**引擎在施加 AttributeModifier 时另做的**（或需要状态"变更通知"才会让绘制模块重新求值）。

#### 6.3 两个必须记住的坑（✅ 仍适用）

1. **`Drawable+0x264` 那 60 字节是引擎每帧重算的缓存** —— 直接 `poke` 会被覆盖（实测几百 ms 后变回 0）。
   改模型条件**必须**把目标 15 dword 写进 `Drawable+0x2DC`（或 `+0x2A0`，是它自己的两个内部缓冲），
   再 `__thiscall` 调 `RVA 0x12F360(ecx=Drawable, src, 1, 0)`。这样才站得住。
   （⇒ 早前"poke MC FROZEN 无效"的结论作废，那次也是被覆盖了。）
2. **直接写 `ObjectStatus` 位（`Thing+0x80..`）没有"变更通知"** —— 绘制模块可能不会重新求值。
   这是当前最可疑的缺口。状态位域结构：基址 `Thing+0x80`，`bit=1<<(idx&31)`，`word=idx>>5`。

#### 6.4 modifier 路线（⚠️ 部分过期 —— 缺口已由 §7 补上）

> ⚠️ 旧版本这里写的 `0x417FA0` / `0x4A6BE0` / `sub_4A9C80` **是 VA，不是 RVA**。

#### 6.4b 冰覆盖向量 `Drawable+0x244/248/24C`（🗑️ 未定案 + 危险 —— 勿复用）

- 它是 `Drawable` 上的 `std::vector<overlay*>`：`sub_520440` = 非空判断、`sub_520460` = 取 `[+4]` 最大者、
  `sub_535FE0` = 移除；元素指向**共享对象 `0x0F50F740`**。
- 同一台天启冻结前后干净 diff 里，**这是 Drawable 侧唯一的"冰专属"变化**。
- **它不每帧重建**（手写进去的值能存活 ≥12 s，且扛过单位移动）；旧笔记"每帧重建、poke 无效"**作废**。
- 但**注入 `+0x244` 是否就能出冰，本轮没能定案**（测试车无法确认在画面内）—— 不要据此下结论。
- ⚠️ **它是引擎"拥有"的容器**：单位被销毁时引擎会 `free()` 它的 buffer。
  **绝不许把 DLL 自己的内存（`/scratch`、全局量）当作它的 buffer 写进去** ——
  2026-10-16 10:49 就是这样把游戏搞崩的（引擎析构时 `free(0x9F191508)`，崩在分配器 `sub_A6D690`
  的 `mov [ecx+8],edx`，写了地址 `0x8`）。要造 backup buffer，必须是游戏堆内存。

### 7. modifier 通道 —— 引擎施加 / 解除（✅ 现役）

**三个引擎函数，原版即具备，与日冕桥无关**（桥只是把这几个引擎函数暴露给了 Lua）：

| 用途 | 地址 | 调用形态 |
|---|---|---|
| modifier 库查表 | RVA `0xA6BE0` | `__cdecl (container = 0xC5E07887, nameHash, out)` → modifier 对象 |
| **施加** | VA `0x7181F0` | `__thiscall (this = Thing, modifier, duration)`，handler 槽 `vtable+0x1D0`，`ret 8` |
| **解除** | VA `0x718300` | `__thiscall (this = Thing, modifier)`，handler 槽 `vtable+0x1D8`，`ret 4` |

两者都在 `[Thing+0x328]` 找 handler，再经 handler vtable `+0x84` 取查找器 —— 结构对称。
解除函数的出处：桥 `ObjectUnloadAttributeModifier`（VA `0x10020740`）主逻辑 `mov eax,[0x1016A45C]; call eax`，
活进程里 `[0x1016A45C] = 0x00718300`。

**`duration` 的单位是「帧」，15 帧/秒**（扫参实测）：`10 → 0.8 s`、`20 → 1.7 s`、`50 → 3.4 s`、`100 → 6.6 s`、
`500 / 5000 / -1 → > 15 s`。⇒ 冻 N 秒传 `N*15`，**不需要 `-1`**。
（`-1` 在铁幕与冷冻上行为不同：铁幕 12 min 内自行过期，冷冻 > 9 min 仍在。）

**实测（对己方单位，均 `ret=1`）**：`AttributeModifer_CryoBeam_10` → **冰涂装 + 不能动 + 技能锁 + 周围禁建**；
**无冻结音效、无易碎**。

> ℹ️ **说明（2026-10-16 19:0x）**：一度出现"技能可用 / 动画正常 / 无音效"的观察，
> 但那出在**我用 curl 手抄复刻 `ApplyFreeze` 且漏步**的实验里（只做了 `SetStatus`，缺槽位字段与速度节点）
> —— **不能据此否定 `CryoBeam_10`，那条标注已撤销**。
> 行为锁 / 音效 / 技能锁的**可靠实现 = 当时的 `/freeze?mode=0`**（`ApplyFreeze` 六步，全护栏；已随功能移除）。

**（历史）"完整冻"组合**：`/freeze?mode=0`（音效 + 行为锁）**+** 施加 `CryoBeam_10`（冰涂装 + 周围禁建）；
解冻走引擎 `0x718300`。

**状态字**（引擎施加以外写，只作判据，**不是开关**）：

| 施加 | `Thing+0x98` | `Thing+0xD4` |
|---|---|---|
| 冷冻 | `0x4000`（bit14） | —— |
| 铁幕 | `0x10080`（bit7 + bit16） | `0x2000`（bit13） |

> ⚠️ 已实测证伪「直接改状态位即可冻 / 解冻」：poke `+0x98` bit14 → 不冻；清位 → 不解冻
> （引擎的判定在它内部的 modifier 列表）。**必须走引擎函数**。
> 两个函数都**不改 `Body`**（各扫 0x0..0x800 零变化）；`Body = [Thing+0x33C]`。

**名字可解析性（原版数据，查表实测）**：`AttributeModifer_CryoBeam_02.._10`、`AttributeModifier_IronCurtain`
（`0x6516AA2D`）、`AttributeModifier_CryoSpray`、`AttributeMod_MAP_ObjectsFrozen`（`0xCDFDC01C`）**存在**；
而 `AttributeModifier_MAP_ObjectsFrozen`、`_Frozen`、`_PermanentFrozen`、`_CryoFrozenArmor`、`_ObjectsFrozen`、
`_Chrono`、`_Shrink`、`_Nuke` **不存在**（前缀与拼写敏感）。

**社区口径**（语雀 `ra3mapwiki`《LuaAPI-LuaBridge》）：`ObjectLoadAttributeModifier(unit, name, [frameCnt])` /
`ObjectUnloadAttributeModifier(unit, name)` —— 正是上面这两个引擎函数；另有 `Unit:add_status / remove_status`、
`Unit:add_model_state(states, 秒)`。

**★ 原版易碎：实测确认存在，但只能走完整冷冻流程（需召雪机，已被否决）—— 现由下面的社区方案替代**（2026-10-16 17:52 受控实验）：

**受控测量**（视角中心；靶 = 敌方指挥中心 2000 血；打手 = **我方**守护者坦克；冻结 = **我方**冰冻直升机）：

⇒ **放大 ≥17.6×**。这解释了肉眼观测的「冻满后一击打掉几千血」。**`CryoBeam_10`（挂档位）不触发易碎**
（它不累积冷冻值）；触发条件 = **引擎光束把冷冻值照满**（雪机 `OrderAttack` 持续照射到 `+0x090` PARALYZED）。

**实验方法学（复用）**：召出的**敌方单位会自动攻击附近目标**（污染未冻基准）、**我方单位不会** ⇒

**「一键易碎」内存层判定：不可行**（2026-10-16 晚，三重验证）：
① **同一对象密集时间序列**（0.5 s 采样，`Thing/Body` 各扫 0..0x1000，只取"冻满那一刻才变"的字段）——
**仅 7 个状态位变化**：`Thing+0x090|0x20000` / `+0x098|0x4000` / `+0x0CC|0x8000000` / `+0x26C=2` /
`+0x274=0x3FFFFFFF` / `+0x470`(0x2000→0) / `Body+0x100|0x2000`；
② 跨对象对照（冻 A vs 不冻 B，同型）无额外差异；
③ **poke `Body+0x100 |= 0x2000`** —— 位**写进去且保持住**，但**伤害 18 发全是 67.5** ⇒ 伴随位、非开关。
⇒ **「护甲覆盖」与「冷冻值」都是引擎内部状态，不在对象内存的可见字段里** ⇒ `poke` 做一键易碎走不通。

**加速方案（实测 · ❌ 已被用户否决 —— 仅留证据，勿作实现路径）**：真冻耗时与雪机数成反比 —— **1 台 9.8 s / 4 台 3.0 s / 8 台 1.9 s**。
`/summon hash=0x509D5101 count=8 owner=3` + 逐个清 `+0x471` bit3 + `/order attack` ⇒ **约 2 秒拿到
「冰 + 定身 + 技能锁 + 禁建 + 易碎(≥17.6×)」**。~~这是当前最快的完整真冻路径~~ ⇒ **否决：不走召唤路径**。

**为什么没有"一键易碎"接口**（社区检索 + 实机双向核对）：
- 桥的 **92 个 Lua 接口无 `set_armor`**；社区 Lua 库（`Ra3CoronaMapLuaLib`）同样只有 `get/set_health`、
  `suffer_damage`、`add_status / add_modifier / add_model_state` 三族。
- modifier 的**属性表**（modifier 对象 `+0x000` → 表）只含「**状态位掩码 + 资源指针**」，**无护甲字段**：
  `IronCurtain` 表 `+0x090=0x00010080`（= 实测 `Thing+0x98` 铁幕位）、`+0x094=0x0F7504B8`；
  `CryoBeam_10` 表 `+0x054=0x00004000`（= 实测冷冻位）、**`+0x058=0x0F7506A0`（冰覆盖资源对象 ——
  与真冻单位 `Drawable+0x244[0]` 是同一个）**。
- 数据侧 147 个 AttributeModifier **无易碎类**；165 个 ArmorTemplate 中特效类只有 `CryoBeamFrozenArmor` /
  `InvulnerableArmor` / `ShrinkRayEffectArmor`。
⇒ **换甲是引擎"冷冻值满"时的内部行为，数据/接口层没有入口** —— 只能走完整冷冻流程（引擎光束照射）。

**真冻判据（更正）**：判定"真冻"看 **`Thing+0x090` bit17（`0x00020000` USER_PARALYZED）**；
`Thing+0x98` bit14 只是**伴随位**（单挂 `CryoBeam_10` 会置它，但**不置** `+0x090`）。
完整指纹另含：`Thing+0x0CC=0x08000000`、`Thing+0x26C=2`、`Thing+0x274=0x3FFFFFFF`、
`Drawable+0x188`(TintEnvelope\*＝冰色)、`Drawable+0x244`(覆盖 vector，元素 = 冰覆盖资源)。
（`Thing+0xF4` = Drawable；`Drawable+0x138` 回指 Thing。）

**★ 易碎替代：社区 `MAP_` modifier（✅ 已实测，2026-10-16 晚）**：

原版"换 `CryoBeamFrozenArmor`"无入口，但**日冕地编提供一批 `MAP_` 前缀 modifier**（语雀《单项AttributeModifier清单》），
可**直接叠加**在选中单位上 —— 走的是**同一条 `0x7181F0` 施加链**，不需要召唤任何单位。

| modifier | 哈希 | 效果 |
|---|---|---|
| `AttributeModifier_MAP_ARMOR_Up` | `0x505EBD44` | **减弱护甲** —— 实测单发 **67.5 → 736（×10.9）** |
| `AttributeModifier_MAP_HEALTH_MULT_Down` | `0xAC47C5FF` | **血量上限 ×0.9/层**（线性可叠，无触底） |
| `AttributeModifier_MAP_SPEED_Down` | `0x46C6A82B` | 减速（"定身"的平滑版） |
| `AttributeMod_MAP_ObjectsFrozen` | `0xCDFDC01C` | 单位变**实心冰块模型**（纯视觉，语雀注明"验证有效"） |

**实测**（视角中心召敌方建造基地 4000 血 + 我方守护者坦克；`ARMOR_Up`×30 + `HEALTH_MULT_Down`×30，各 900 帧）
⇒ 血量上限 **4000 → 169.6**；坦克开火 **0.9 秒摧毁**。

**两个坑**：① `duration = -1` 约 **12 秒**就过期，**一律给明确帧数**（15 帧/秒，900 = 60 秒）；
② 护甲削弱**有下限**（叠 99 层也只到 ×10.9）；要更狠就叠 `HEALTH_MULT_Down`。

元素 = `0x0F7506A0`（**冰覆盖资源对象**，与真冻单位同一个）—— **载具 / 建筑均生效**（守护者坦克 + 建造基地都验过）。
