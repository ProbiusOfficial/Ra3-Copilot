# 动态注入与 DLL 热重载

目标：改完代码不必退出游戏 —— 「游戏内卸载 → 重新编译 → 重新注入」一条命令完成。

范围：`ra3-copilot` 的注入/卸载链路（`injector.exe` ↔ `ra3copilot.dll`）。

---

## 一、链路

```
hot_reload.bat
 ├─[1] injector.exe --unload ──► POST 127.0.0.1:17832/unload
 │        └─► 游戏内实例：下一帧拆卸全部 hook 并 FreeLibraryAndExitThread（真卸载）
 │        ◄── 轮询进程模块表：ra3copilot 消失 = 成功（DLL 文件锁随之释放）
 ├─[2] call build.bat ──► build_out\ra3copilot.dll ──► 覆盖项目根 ra3copilot.dll
 └─[3] injector.exe ──► CreateRemoteThread(LoadLibraryW) 注入
          ◄── 复核：模块表出现 + 17832 /ping 应答
```

游戏未运行 / 未注入时：`--unload` 幂等返回成功（已是目标状态）。

## 二、卸载流程（DLL 侧）

触发：`POST /unload` → `RequestUnload()` 置位 → 渲染线程在**下一个 Present detour 内**执行拆卸。

**为什么在 Present detour 内**：这是全进程唯一「我们确定可控、且能证明此刻没有别人在 DLL 里」的时机 —— 进来先停掉全部自建线程，之后剩余入口（d3d9 detour、窗口过程）都由 `g_inHook` 计数封口。

| # | 动作 | 失败处理 |
|---|---|---|
| 1 | 停 HTTP 线程：`HttpApiStop()` + join（≤4s）—— 端口 17832 随之释放 | 中止 |
| 2 | 停输入线程：置退出标志 + join（轮询 Sleep(25)，秒退） | 中止 |
| 3 | 还原窗口过程 `SetWindowLongPtrW(GWLP_WNDPROC)` + 还原崩溃过滤器 | — |
| 4 | `ImGui_ImplDX9_Shutdown` + `ImGui_ImplWin32_Shutdown` + `DestroyContext`（此刻 device 有效，正是释放时机） | SEH 兜住 |
| 5 | 回写 20 个功能 hook 原 5 字节（`RemoveHooks`）+ 逐站回读校验 | 中止（保命） |
| 6 | 拆除全部 MinHook hook（`MH_DisableHook` ×6：d3d9 五钩 + Find 学习钩） | — |
| 7 | 置 `g_silent` → 卸载线程：等 `g_inHook` 归零 + 100ms → `MH_Uninitialize` → `FreeLibraryAndExitThread` | — |

**中止 = 不 FreeLibrary**：任一步失败即停止（本帧继续正常渲染，日志写明原因）——「拆一半就卸载」比「不卸载」危险得多。中止后 `g_unloading` 不复位（不做自动重试），重新注入新 DLL 即恢复。

**安全护栏**

- `g_inHook`：5 个渲染 detour（Reset/Present/EndScene/SwapPresent/SetTransform）+ 窗口过程的执行计数 —— FreeLibrary 前必须归零（无人还在 DLL 代码里）。学习 hook（Find）与 stub 不计数，由「已拆除 + 100ms 安全间隔」兜底（它们无 IO、无等待，执行时间是纳秒级）。
- Present 在拆卸发生时正在栈上：本次调用继续穿 MinHook trampoline 完成渲染 —— trampoline 在 MinHook 内存池（独立于 DLL 映像），所以「边拆边用」成立。
- 功能 hook 的 code cave（`AllocCave` 的 64B/站）不回收：site 还原后无人再跳入，泄漏 ≈1.3KB/轮，可忽略。MinHook 池由卸载线程 `MH_Uninitialize` 释放。

## 三、工具

| 命令 | 作用 |
|---|---|
| `injector.exe --unload` | POST /unload → 轮询模块表等 `ra3copilot` 消失（真卸载判据，超时 15s）；未加载时幂等成功 |
| `injector.exe` | 注入（默认同目录 ra3copilot.dll）→ 复核模块表 + HTTP /ping |
| `injector.exe --status` | 只查游戏进程 |
| `hot_reload.bat` | 卸载 → 构建 → 注入，一键（对局中直接跑） |
| `POST /unload` | 游戏内触发卸载（`injector.exe --unload` 的第一步） |

**防双实例**：注入前预检模块表，同名模块已加载则拒绝注入。重复注入的第二份映像有独立 `.data`/`.bss` —— 功能 hook AOB 校验读到第一份写入的 `E9` 而 fail-closed 跳过、HTTP 端口被旧实例服务，结果是「命令成功返回、跑的还是旧代码」。要换版本必须走「卸载 → 注入」。

## 四、硬约束与待实测

1. **线程模型假设**：Present detour、功能 hook stub、窗口消息都在游戏主线程 —— 「单线程自拆卸」的前提（`g_inHook` 计数在多线程下同样正确，只是会让卸载多等）。实测法：各入口记录 `GetCurrentThreadId()` 比对；卸载日志已带执行线程 tid。
2. **卸载后同路径重载**：模块引用归零后 `LoadLibraryW` 重新读盘 → 新构建生效 —— 由 `hot_reload.bat` 全流程验证。
3. 与 `0x205240` 的 stub 机制（运行中会被改成 `ret 0x10`）的交互 —— 待复核。
4. 中止路径（HTTP/输入线程卡死、回写失败）的实际表现 —— 待实测。

## 五、实机验收清单

首次验收（在无关紧要的对局做）：

1. 对局中 `POST /unload` → 模块表里 `ra3copilot` 消失；游戏继续正常渲染与操作（无功能）。
2. `injector.exe --unload` 端到端：触发 → 15s 内报「卸载完成」。
3. `hot_reload.bat` 全流程：卸载 → 构建（root DLL 覆盖成功，不再提示被锁）→ 注入 → `/ping` 应答 → 新功能生效。
4. 连续 3~5 轮 → 进程模块数不增长、无崩溃；`ra3copilot_log.txt` 里每轮 `[卸载]` 行完整。
