# 建造页「科技锁定」黑锁 — 根因与破除

> 状态：**已解决**（2026-10-22 实测通过）
> 一句话：UI 直接调 `0x43EA70` 判断「模板在不在玩家的可用对象集合里」，返回 1 就是黑锁；
> 加一个按 owner 收窄的桩即可解锁。

## 一、现象

RA3 / 日冕 1.12 战役对局里，建造面板部分格子显示黑色挂锁，悬停 tooltip 只有一行「科技锁定」。
锁格**不显示单位图标、也不显示单位名**，且会跨多个分类页（建筑页、载具页都可能出现）。

典型样本（某局实测）：**机场**、**起重机回收场** 各一格。

## 二、根因

`GUI:BuildabilityDisabled` 是 exe 里 146 条 `GUI:` 字符串中**唯一**的「禁用原因」串
（VA `0x00C814EC`）。它的两个引用点 `0x6C5DA4` / `0x6D6BFB` 只是取本地化串拼 tooltip，**不是判定点**。

真正决定按钮是否画锁的是 **`0x43EA70`**：

```
__thiscall(ecx = Player*, [esp+4] = Template*) -> al，ret 4

bit9 = ([Template+0xC0] >> 9) & 1
if (bit9) { if (Player->[0x105] == 0) return 1; }
else      { if (Player->[0x104] == 0) return 1; }

// 遍历 Player+0x200 链表，比对 [[Template+0x14]] + 4 这个 key
找到   -> al = 0        （可用）
没找到 -> al = 1        （不可用 → UI 画黑锁）
```

语义：**「该模板在不在这个玩家的可用对象集合里」**。战役剧情锁科技，就是把模板从该集合里摘掉。

### 为什么 Science / Buildability 都不是门

`0x43EA70` 有四个调用点：

| 调用点 | 说明 |
|---|---|
| `0x4451FE` | `0x4451F0`（Science）内部第一道关 |
| `0x6B7089` | UI |
| `0x6BB228` | UI |
| `0x6BB4E2` | UI |

**三个 UI 调用点直接调它、绕过 `0x4451F0`。** 所以给 `0x4451F0` 打桩时，
`0x43EA70` 依然返回 1，黑锁一动不动 —— 这是之前反复误判的直接原因。

## 三、实现

`features.cpp` 的 `kHooks[]` 新增一项：

| 名字 | RVA | AOB（10 字节） | replayLen |
|---|---|---|---|
| `ClanGate` | `0x43EA70` | `8B 44 24 04 8B 90 C0 00 00 00` | **10** |

AOB 在 exe 内有 2 处命中（`0x43C720` / `0x43EA70`），但安装是按**固定 RVA + 原地校验**，
只认 `0x43EA70`，不影响。

**指令边界（务必按这个，写小了会崩）**：

```
+0   mov eax,[esp+4]        4 字节
+4   mov edx,[eax+0xC0]     6 字节
+10  shr edx,9              ← jump-back 目标
```

stub `ClanGateCaveStub`（`stubs.asm`）：

- `g_flags[0x1B]` 关闭 → 重放两条原指令后跳回 `+10`（完全等价原行为）
- 打开且 `ecx == g_localPlayerObj` → `xor al,al; ret 4`（= 可用）
- 打开但 `ecx` 不是本机玩家 → 走原路径

**必须按 owner 收窄**：引擎在 AI 路径上对这个返回值的假设与玩家路径不同，无条件放行会出问题。

## 四、用法

**界面入口：杂项操作 → 「移除科技锁定」**（勾上即生效，取消即恢复，实时写 `g_flags[0x1B]`）。

```
POST /toggle?f=0x1B&on=1     # 解锁（当前对局生效，重注入/重开游戏后回到关闭）
POST /toggle?f=0x1B&on=0     # 恢复
```

实测效果：

- 黑锁格变正常图标，**可直接放置建造**
- 建造列表**不会**多出敌方或无关建筑（列表由 CommandSet 决定，这个函数只管「能不能用」）
- 无崩溃、无卡顿

| `0x4451F0` Science | 打桩后返回值 `0→1` 已验证，**UI 黑锁无任何变化** |

## 六、附带经验

- **`0x6C5D90` 探针是有效的手法**，前提是确信鼠标停在锁格上。它构造
  `GUI:BuildabilityDisabled` tooltip，只在按钮被判定不可用时调用，`a1 + 0x18` 就是模板指针。
  问题在于普通按钮也会走同一构造器，需要多次采样交叉比对。
- 定位「某道门」的正确顺序：**先确定 UI 走哪条链**（用探针抓对象），再反推函数，
  不要从「看起来像判定函数」的静态清单里逐个试。

## 七、扩展建筑：补全列表 + 解除灰色（2026-10-22）

战役建造页比扩展模式少了 **胡杨防空导弹系统**（`0x6094F50D`）与
**礁石岸防导弹要塞**（`0x2D270F77`，双用途巡航导弹塔）。这是两件事，各有各的门。

### 7.1 列表里没有 → CommandSet

建造页按钮列表由列表构建器 `0xACB330` 一次性生成：按名字哈希查 store
（`0x4DF970([0xCD8D00], key)`）得 CommandSet，再按 `vt+0` 的数量循环 `vt+0xC(i)` 取按钮定义。

战役局实际用的是 **`0x0CCE8730`**（`SovietConstructionYardCommandSet` 变体，17 条），
而扩展完整版是 **`0x0CCE8848`**（19 条）。两者 def 指针逐条共享，只差这 2 条。

做法：`CommandSetProbeCaveStub`（站点 `0xACB352`，构建器刚拿到 cs、循环 new 按钮之前）
调 `Ra3BuildExtFix(cs)`，作用于 `g_flags[0x1D]`：

- 邻域扫 `cs ± 0x40000` 找 vtable `0x00BE9178` 的同族实例（实测 B 与 C 只差 `0x118`），
  命中不了才全内存兜底；
- **但 `cs` 和它的 `inner` 常常分属两个不同的堆簇**（实测战役局：
  `cs=0x0CCC71E0`、`inner=0x08E21280`，而同族完整版 `cs=0x08E21270` 就在这个 inner 旁边）。
  只扫 `cs` 邻域会一路扫到本簇的变体，永远看不到完整版 ⇒ 必须**再按 `inner` 邻域补扫一次**。
  这是 2026-10-22 苏联战役"开了开关仍 6 格"的真正原因（`/buildext` 显示 `生效=0`）。
- 若目标 cs 缺这两个哈希，把它的 `cs+4`（inner 指针）指向扩展完整版的 inner ——
  count / base 一起跟过去，**不扩数组、不造对象**。

⚠ **地址不可硬编码**：CommandSet 实例地址每次加载场景（换战役任务）都会重新分配，
同一进程内才稳定。文档里的地址只作样本，代码与脚本一律运行时扫。

⚠ **时序**：`0xACB330` 只在「进对局」那一刻跑一次。重选建造者、切页签都不会重跑。
改 CommandSet 后必须重开一局；`0x1D` 要在**进对局前**就是开的状态。

⚠ **性能**：全内存扫 2 GB 第一版要 4.2~4.9 秒（把游戏卡死）。正解是邻域扫（毫秒级），
全扫只留给 `/buildext` 诊断端点。

### 7.2 列表里有但画灰 → `0x445250`

按钮可用性由 UI 按钮对象的 vtable `0x00C88518` **slot13 = `0xABB6F0`** 每帧刷新：

```
0xABB6F0(按钮对象*)
  ├─ call 0xABB360                      ; 前置快速判定，真则直接返回
  ├─ 取 [按钮+0x18] = Template*；看 [Template+0xD8] bit15
  └─ 有 Player 时 → 0xABB7A6 / 0xABB757 两条
        最终 0xABB812:  ecx = Player
                        push Template
                        call 0x845250        ← Buildability，唯一的灰/亮门
           al=0 → 0xAB7040  setDisabled → UI 画灰
           al=1 → 0xAB7000  setEnabled
```

`0x445250`（VA `0x845250`，`__thiscall bool(Player*, Template*)`, `ret 4`）：

```
if (!Template) return 0
if (!0x4451F0(Player, Template)) return 0     ← Science：前置科技 / 0x43EA70
s = 0x7DF770(Template)                        ← 取 [Template+0x14]+0x1AC（缓存兜底）
if (s == 2) return 0
if (s == 1) return 1
if (s == 3 && Player->[0x2C] != 1) return 0
return 1
```

扩展建筑在战役局缺前置建筑 / 科技 ⇒ `0x4451F0` 返回 0 ⇒ 灰。
但引擎**落点判定是通的**：`GET /buildable?hash=0x6094F50D&x=..` 返回 `code=0 可建`。
所以这纯粹是 UI 层的按钮状态问题，与「能不能造」无关。

**两种解法**

| 开关 | 站点 | 粒度 | 说明 |
|---|---|---|---|
| `0x1A` `FID_SCIALL` | `0x4451F0` | 全局 | 对本机玩家恒真 → **所有**建筑都忽略前置科技，灰按钮一律变亮 |
| `0x1E` `FID_BTNENABLE` | `0xABB6F0` | 精准 | 只对 `6094F50D` / `2D270F77` 直接 `setEnabled(true)` 并返回 |

`0x1A` 影响面大（会让原本该灰的都变亮），日常用 `0x1E`。

`BtnEnableCaveStub` 要点：

- `ECX` = 按钮对象，`[ECX+0x18]` = Template*，`[Template+8]` = 名字哈希；
- 命中目标哈希 → `mov eax,0xAB7000; call eax`（`setEnabled(true)`，ecx 仍是按钮对象）→ `mov al,1; ret`；
- 否则重放 `sub esp,8 / push esi / mov esi,ecx`（6 字节）跳回 `0xABB6F6`；
- 不碰 `ebx/esi/edi`，只用 `eax/ecx`（调用者都不保留）；
- AOB `83 EC 08 56 8B F1 E8 65 FC FF FF`（11 字节，全 exe 唯一；只取前 6 字节作 AOB 会命中 265 处，别用）。

### 7.3 用法

```
杂项操作 → 「补全扩展建筑」    （0x1D，进对局前开）
杂项操作 → 「扩展建筑可点」    （0x1E，随时开）
```

实测：两栋建筑出现在支援建筑物页签，正常图标、可点、可放置。
卖掉前置科技建筑后按钮仍保持可点（`0x1E` 每帧强制），符合预期。

### 7.4 四阵营通用（2026-10-22 补齐）

第一版只写了苏联的两栋，`builder` 签名也只认苏联的四栋主建筑 —— 所以**只对苏联有效**。
实测内存发现各阵营结构完全同构，各有一对「战役版 / 扩展完整版」CommandSet，
def 指针逐条共享，扩展版只多 2~4 条：

| 阵营 | 战役版 | 完整版 | 完整版多出来的 |
|---|---|---|---|
| Soviet | `0CCE8570`(15) | `0CCE8848`(19) | 胡杨防空导弹系统 `6094F50D`、礁石岸防导弹要塞 `2D270F77`、`SovietCrane`、`0D019050` |
| Allied | `0CCED830`(15) | `08E45CF0`(18) | 盟军重型火炮防御基地 `19681796`、盟军宙斯盾大型防御基地 `32535841`、`Upgrade_AlliedTech4` |
| Celestial | `08E42390`(14) | `08E42180`(16) | 天朝能量加特林塔 `F84AA5E2`、天朝能量轨道炮基地 `CCA5F13A` |
| Japan | `0CCEB130`(16) | `08E3F6B0`(20) | 点防御控制塔 `F6CAF260`、神风指挥塔 `7117987E`、巨型要塞舰 `5066384B`、欧米伽湮灭炸弹 `078AB8D6`（日冕里日本建筑全叫 `*Egg`） |

（每个阵营还有若干中间变体，如天朝 `08E434A0`(17)、盟军 `08E45F30`(17)、日本 `08E3F770`(20，战车工厂是 `*_Enhanced` 版)；
`Ra3BuildExtFix` 取「哈希集 ⊇ 当前」里 count 最大的那份。）

改造两处：

1. `builder` 识别签名按阵营分组（`SIG_BLD[4][4]`），任一组四栋全命中即认作建造者。
   **苏联那四个哈希在盟军 / 天朝 / 日本的 cs 里一个都没有** —— 单组判定会把它们全漏掉，
   这是「只对苏联有效」的直接原因。
2. `hasExt` / 按钮强制可用改成查 `EXT_BLD[10]` 白名单（四阵营），
   `BtnEnableCaveStub` 通过 `Ra3IsExtTpl(hash)` 判定，不再在 asm 里写死哈希。

改造后 `/buildext` 显示「建造者=22 含扩展=11」（此前 4 / 2）。

实测（日本战役局）：`生效=1 最近 cs=0CCEB130 -> inner=08E3F7C0`，
即构建器拿到的正是战役版 16 条那份，被换成完整版 20 条；建造页正常、按钮可点。

⚠ 探针 `CommandSetProbeCaveStub` 的顺序：**必须先在 `Ra3BuildExtFix` 之前记 `eax`**。
Fix 返回后 `eax` 是新 inner，不再是 cs —— 早期版本记在 Fix 之后，读出来的 `S[i]` 因此对不上号。

工具：`tools/_clanpair.py`（按「A 是 B 的按序子序列」找同族配对，不依赖任何阵营哈希，可复用到其它 mod）、
`tools/_csnames.py`（dump 某 cs 的全部 def + 模板名）、
`tools/_prefhunt.py`（按名字前缀找阵营的 CommandSet，日本是靠它定位的）。

### 7.5 「免基地前置」不在建造链上（2026-10-23）

协议页的 **「免基地前置」**（`/unlock`，裸 patch `RVA 0x43B81B`）**解除不了科技前置**，任何关卡都不行 ——
它改的是 `0x83B740`，而 `0x83B740` 全 exe **只有 1 个调用者 `0x4D7DD7`**（`0x4D7D80` 内遍历 `Player+0x1260` 建筑列表），
建造按钮链一次都没碰它：

```
0xABB6F0  建造页按钮可用性刷新（vtable 0x00C88518 slot13）
  └─ 0xABB812 → 0x845250  Buildability
       ├─ 0x8451F0  Science
       │    ├─ 0x83EA70   ClanGate：模板不在可用集合 → ret 0（黑锁）
       │    ├─ [Template+0xD8] bit23 为 0 → 直接放行
       │    └─ 0x844DF0   批量查 PlayerTech（科技表，回调 0x83B280）→ 不满足 ret 0
       └─ 0x7DF770 取 status：2 → 灰；3 且 Player+0x2C==1 → 灰
```

⇒ 「缺前置建筑」与「缺前置科技」是两道不同的门，只有前者可能被 `0x83B740` 波及。
早期担心的「`0x83B740` 恒真会让建造菜单全解锁」也因此不成立。

四个开关的边界：

| 开关 | 站点 | 管什么 |
|---|---|---|
| `0x1A` `FID_SCIALL` | `0x8451F0` | 前置**科技**（PlayerTech）。本机玩家恒真 → 战役灰按钮变亮、可建 |
| `0x1B` `FID_CLANGATE` | `0x83EA70` | 模板在不在**可用对象集合**（黑锁 + 「科技锁定」tooltip） |
| `0x1D` `FID_BUILDEXT` | `0xACB352` | 建造页里**有没有**这格（CommandSet 列表） |
| `0x1E` `FID_BTNENABLE` | `0xABB6F0` | 只对 `EXT_BLD` 白名单那 10 栋强制 `setEnabled` |

界面按「缺的是哪种抑制」拆成三个开关：

| 开关 | 绑定 | 管什么 |
|---|---|---|
| **解除科技锁定** | `0x1B` | 战役剧情 / 剧本挂的黑锁（建造页锁图标） |
| **忽略前置科技** | `0x1A` + 许可授予 | 前置科技与初/中/高/最高许可（议会批准的那套证件） |
| **启用扩展模式科技** | `0x1D` + `0x1E` | 补全扩展建筑并让其可点，四阵营通用 |

三者都只对本机玩家生效，电脑不受影响；许可按对局授予，换关要重新勾。

### 7.6 「许可」是 Upgrade，不是 Science（2026-10-23）

生产面板里「要求：中级许可 / 最高许可」的灰按钮，**与上面四个开关都无关**。
对照实验：`0x1A` 开/关两次，`0x8451F0(Player, PrismTank)` 与 `0x845250` **都返回 1** ⇒ 灰不是 Science / Buildability。

「许可」在日冕里是**玩家级 Upgrade**，走 `Player` 的升级集合，Science 链完全不看它。内部名（进程内 intern 串实测）：

| 阵营 | 名字 |
|---|---|
| 盟军 | `Upgrade_AlliedTech2` / `Tech3` / `Tech4`（**没有 Tech1**） |
| 神州 | `Upgrade_CelestialTech_RANK1` / `RANK2` / `RANK3` |
| 帝国 | `Upgrade_JapanBarracksTech2..3`、`JapanWarFactoryTech2..4`、`JapanNavalYardTech2..4` |
| 苏联 | 不用 `Tech` 命名，未定位 |

授予走现成通道（`ProtoGrantUpgrade` → 注册表 `[0xCDBBF0]` 查表 → `0x44D7C0(Player, tpl, 2, 1)`）：

```
POST /upgrade?name=Upgrade_AlliedTech4&mode=2      # 单条
POST /allclearance                                 # 上表全部，命中即授
```

授予已并入 **忽略科技前置**：勾选时自动调 `ProtoGrantAllClearance`，不再单独占一个按钮。

⚠ 只作用于**当前对局**：Upgrade 是玩家身上的标记，换关/重开就没了，需要再点一次。
⚠ 名单是全局注册表，跨阵营名字同样能命中 —— 一次会把三家的许可都授上，多出来的对当前局无影响。

# 八、Steam 版扩展建筑（补全 + 解除灰色）— 2026-10-26 打通

> 零售版的做法（§七）在 Steam 上**一条都不成立**，两版必须分开走。
> 下面这套是 Steam 版实测通过的实现，零售仍用 §七 的旧路径。

## 8.1 两处根因（都跟「结构解不出」无关）

1. **CommandSet vtable 早就解出来了** —— 用「vtable 逐项函数重定位 + 找连续排列」，
   Steam = **`0xBF0838`**（零售 `0xBE9178`）。早期用单个 `vtable[0]` 当指纹搜三连指针，
   撞车太多所以误判「解不出」。
2. **真正的对象布局**（`tools/inspect_cs.py` 只读取证）：
   ```
   inner+0x00 → desc_holder(16B)   +0 = 0xEC066D65(恒定类型) +4 = key(sage_hash) +0xC = 0x19
   cs = desc_holder + 0x18，本体 16B：
        +0x00 外层 vtable(0xBF0848)  +0x04 refcount
        +0x08 内层 vtable(0xBF0838)  ← 游戏拿到的 cs 就是这里
        +0x0C inner
   inner+0x04 = count   inner+0x08 = 按钮数组（内联，= inner+0xC）
   ```
   ⇒ **直接写 `cs+4` 改 inner 会同时破坏 refcount 与 map 的 key**，点开列表必崩。

## 8.2 `0x1D` 补全列表：换句柄，不改对象

建造页的 cs 是**查表**拿到的，就在这一步换掉返回值：

```asm
; 零售 0x6CB330 / Steam 0x662400（逐条同构）
mov  ecx, [0xCD8D00]   → Steam 0xCDDEA0（CommandSet 注册表）
call 0x4DF970          → Steam 0x521370（key → cs 句柄）
mov  ebx, eax          ← 站点（零售 0x6CB352 / Steam 0x662422，8 字节）
```

hook 这 8 字节（AOB `8B D8 85 DB 89 5C 24 18`），把 `eax` 换成同族完整版句柄。
**不写任何游戏内存**，refcount 与 map key 天然保持一致。

候选筛选（缺一不可，否则会跨阵营误配）：
- 同 `grp`（建造者签名组，`SIG_BLD` 命中哪组 = 哪个阵营/族）
- 完整版 `count >= 原版 count`，且原版按钮集是它的子集
- ⚠ **不要**拿 `inner+0` 当类型判据：它指向同簇另一个对象（堆地址），每个对象都不同，
  加上这条会把候选全筛空。

实测：`生效=2`（进局构建时替换成功）。

## 8.3 `0x1E` 解除灰色：只在 `setDisabled` 入口改道

**灰不走 Buildability。** `0x650320`（每帧刷新）里本地玩家的按钮分两路：

```
走通 → xor al,al → Buildability → setEnabled  → [按钮+0x3D]=1（亮）
被拦 → call setDisabled                      → [按钮+0x3D]=0（灰）→ 返回 1，外层直接退出
```
所以挂 Buildability（`0x4832C0`）**碰不到**扩展建筑 —— 它的判断在那一层之前就返回了。

正确做法：hook `setDisabled`（零售 `0x6B7040` / Steam `0x64BCC0`，两版逐字节相同）：

```
80 79 3D 00   cmp byte [ecx+0x3D],0
56            push esi
8D 71 08      lea  esi,[ecx+8]
```

命中 `EXT_BLD[]` 模板时**直接 `jmp setEnabled`**（不是 `call`）：原调用者是
`call setDisabled`，栈上有返回地址，`jmp` 过去后 `setEnabled` 的 `ret` 正好回到同一处，
**栈完全平衡**，上下文全是游戏自己的。

`setEnabled` = 同址 +0x40（零售 `0xAB7000` / Steam `0xA4BC80`）。

## 8.4 三条血泪铁律（都在这一处踩过）

1. **stub 里 `popad` 之后不能用寄存器传绝对地址** —— `popad` 会把 EAX 恢复成入口原值。
   写成 `jmp dword ptr [g_target]`（内存间接），或把 `mov` 放在 `popad` 之后。
   （18:16 崩溃：`EIP=00000001 / EAX=00000001`）
2. **绝对地址一律 `moduleBase + RVA`**，禁止 `steam ? RVA : VA`。
   （18:05 崩溃：`EAX=0x64BC80` 是 RVA，正确 VA 是 `0xA4BC80`，连崩 6 次）
3. **永远不要在建造按钮构造函数入口（`0x650320`）手动调 setEnabled 后 `ret`** ——
   那会跳过按钮构造，调用方拿到半初始化对象 → `call [eax+x]` 跳堆 → StackHash 崩。

# 九、扩展模式接入：换 key，不换句柄（`0x1F`）

## 9.1 原理

建造页构建器在查表前会先算出 CommandSet 的名字哈希（key）：

```
0x6CB337  mov ecx,[esi+0x10]   ; 建造者对象
0x6CB33F  call 0x2FCCE0        ; 取 cs key
0x6CB344  mov ecx,[eax]        ; ← hook 点（零售 RVA 0x6CB344 / Steam 0x662414）
0x6CB346  push ecx
0x6CB34D  call <store.find>    ; 拿 CommandSet 句柄
```

扩展模式的 cs 是**平行命名的独立家族**（`XxxEnhancedCommandSet`），战役地图的
`overrides.xml` 只克隆普通版再删条目，扩展版不在篡改范围内。因此在 `0x6CB344`
把栈上的 key 就地换成同名 Enhanced key，`store.find` 直接返回完整版列表 ——
**不写任何游戏对象**，引用计数、`manager+0x40` 的 map key、inner 引用全部不受影响。

站点重放 9 字节到 `call` 之前，跳回点 = 站 + 9；只用 `eax/ecx/edx`，净栈位移 0。

## 9.2 配对表

`src/cs_pairs.h` 是编译期常量表，**24 组**，由 `tools/gen_cs_pairs.py` 从
`.workbuddy/tmp/lcs/pairs.json` 生成：

| 类别 | 组数 | 例 |
|---|---|---|
| 建造厂 | 4 | `SovietConstructionYardCommandSet` → `…Enhanced…` |
| 生产建筑（含分级/地形变体） | 20 | 苏联机场/兵营、盟军机场/船坞/战车工厂、神州战车工厂、日本战车工厂 Water 版 |

配对键是**名字哈希**（`sage_hash(name.lower())`），与游戏数据同源，两版二进制通用。

## 9.3 生效范围

`Thing+0x418` 是 `Player*`。默认只对本机玩家替换（`0x20=0`），因为同一个构建器
也服务 AI 的建造决策；`/toggle?f=0x20&on=1` 放开到全场。

读不到归属时**不替换** —— 宁可少生效，也不要把 AI 的列表一起改掉。

## 9.4 可点白名单：只收「扩展独有条目」

补出列表之后，按钮仍会被 `vtbl+0x44` 判灰（见 §7.2）。`0x1E` 的两处桩
（`Buildable` = 零售 `0x445250` / Steam `0x4832C0`，`SetDisable` = 零售 `0x6B7040` /
Steam `0x64BCC0`）只对白名单放行，而白名单是**运行时求差集**得到的：

```
首次 0x1F 命中时（建造页构建器内部、游戏线程）
  for 每组配对:
    enh  = store.find(enhKey)  → ReadCsNode → 条目模板哈希集合
    base = store.find(baseKey) → 同上
    差集 = enh \ base            → 追加进白名单（≤512 条，去重）
```

只收差集，普通条目一律不进 —— 否则会把它们的科技前置一起放开。
静态 `EXT_BLD`（10 栋扩展建筑）保留作兜底：store 取不到时、或 0x1F 尚未命中时仍可用。

「扩展独有条目」包含生产建筑新增的单位，不只建筑。

## 9.5 `store.find` 的双版本地址

| | store 全局 | `find` RVA | 调用约定 |
|---|---|---|---|
| 零售 | `0x00CD8D00` | `0x0DF970` | `__thiscall`，单参数，`ret 4` |
| Steam | `0x00CDDEA0` | `0x121370` | 同上（两版代码形状一致） |

`find` 的 VA 由 `Pick(retail, steam)` 取，`store` 取 `*(void**)store全局`。

## 9.6 开关与默认值

| 开关 | 默认 | 作用 |
|---|---|---|
| `0x1F` | **开** | 查表前换 cs key + 写 `Thing+0x464`（本路径，唯一在用的） |
| `0x1E` | **不装** | 站点 RVA 已置 0（Buildable / SetDisable 两条都不装），见 §9.8 |
| `0x1D` | 关 | 换 cs 句柄（Steam 专用、全内存扫描 2.8~5 秒；与 `0x1F` 同开互相抵消） |
| `0x20` | 关 | `0x1F` 的范围：1 = 含 AI |

UI 的「启用扩展模式科技」一个勾只驱动 `0x1F`。

`0x1F` 只在**进对局构建建造页那一刻**生效，改完要重开一局。

## 9.8 为什么 `0x1E` 被彻底停用（2026-10-30）

`0x1E` 的三种实现都是在「判定层」替扩展条目开绿灯：

| 版本 | 手法 | 后果 |
|---|---|---|
| v1 | `BtnEnable` 入口跳过构造函数 + 手调 `setEnabled` | 对象半初始化，连崩 6 次 |
| v2 | `Buildable`（`Buildability`）命中即 `mov al,1` | 无效（灰不走这一层） |
| v3 | `SetDisable` 改道 `setEnabled` | 按钮亮了但**点下去被秒取消**；同帧崩 `RVA 0x288470`（链表遍历） |
| v4 | 门钩子 `vtbl+0x44` 直接返回 0 | 崩 `RVA 0x4227A1`（`isEquivalentTo` 取到垃圾模板指针） |

真正的根因不是「判定太严」，而是**显示与判定用的不是同一份 CommandSet**：

```
建造页构建器：0x66240F call 0x33B0F0(producer) → key → find → cs(19 条)
建造判定门  ：0x187BE4 call 0x33B0F0(producer) → key → find → cs(17 条)
                       ↑ 同一个函数，但以前只有构建器那侧被改了
```

于是按钮来自 19 条那份、判定按下标去 17 条那份取 def → 越界 → 点击必崩。
`0x1E` 只是把「亮」这个表象硬掰过来，越掰越容易踩到越界。

`0x1F` 改成**同时写 `Thing+0x464`**（`0x33B0F0` 的第一条指令就是
`cmp dword [ecx+0x464],0 / jne done`，这个槽是引擎留给外部覆盖 key 的旁路，函数自身只读不写），
两个消费者从此拿到同一个 key，显示 / 判定 / 点击取 def 三者统一，
`0x1E` 自然失去存在意义 —— 现已把两条站点 RVA 置 0，桩体保留只为不破坏链接。

## 9.7 诊断

```
GET /extkey       进入 / 已换 / 判不出归属 / 配对 计数，最近一次 key→enh，
```

`Pick` 取了另一列地址）。
