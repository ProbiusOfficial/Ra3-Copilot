# 落点与坐标获取

> 落点 = 召唤/建造/空投时传给 `CreateUnit` 的那个世界坐标，以及指挥单位移动的目标点。
> 本文写这串坐标从哪来、怎么换算、哪些可靠、哪些不可靠。

## 一、核心换算：屏幕像素 → 世界坐标（`0x1ED4A0`）

RVA `0x1ED4A0`（VA `0x5ED4A0`）：

```c
void __cdecl f(void* src, void* dst, int, int);
```

- `src`：**3 个 dword** —— 客户区像素 `(x, y, 上下文)`。第 3 个 dword **不参与运算**
  （实测传 `0` / `1` / `0x12345678`，输出完全一致）。
- `dst`：**4 个 float** —— 该像素射线命中的**地形表面**世界坐标，其中 z 就是地形高度。
- 输入越界不外推报错，照样给结果（实测 `(5000,5000)` 也有输出）。

实测（客户区 1536×960）：

| 输入像素 | 输出世界坐标 |
|---|---|
| `(768, 480)` 客户区正中 | `(3555.9, 5871.4, 210.0)` |
| `(0, 0)` | `(2722.6, 6653.8, 200.0)` |
| `(1920, 1080)` | `(4034.6, 5488.7, 210.0)` |

同一时刻选中单位在 `(3641.0, 5761.0, 210.0)` —— 客户区正中与它吻合，可用来交叉校验。

> **不要走 d3d9 相机矩阵反投影**。实测游戏 `SetTransform(D3DTS_VIEW)` 传的矩阵 `_33` 恒为 `1.0`
> （单位矩阵），3D 相机根本不经过那条通道，反投影永远解不出东西。

## 二、三个落点来源

| 来源 | 取法 | 可靠性 |
|---|---|---|
| **视野中心** | 游戏客户区**正中的像素** → `0x1ED4A0` | 稳。不依赖相机矩阵，也不依赖鼠标；游戏窗口失焦照样算得对 |
| **选中单位** | 首个选中单位 `body+0x38`(x) / `+0x3c`(y) / `+0x40`(z) | 稳。前提是当场有选中 |
| **游戏光标** | `[0x8DAEFC]` 对象 `+0x3c/+0x40/+0x44` → `0x1ED4A0` | ⚠️ 该对象**只在鼠标位于游戏窗口内时刷新**。玩家切出去（例如与 AI 对话）时它停在旧值，走这条会投到「上次鼠标停留处」 |

排列顺序由设置项「落点来源」决定（`g_cfg.posMode`）。每次取落点时**按该顺序逐个试，取第一个成功的**；
三条都失败则回退到「上次成功的位置」。结果记在 `g_posSource` / `g_posDiag`，随召唤日志和接口回执带出。

## 三、接口

### 查

| 端点 | 内容 |
|---|---|
| `GET /view` | 视野中心的世界坐标 |
| `GET /selected_pos` | 当前选中单位的世界坐标 |
| `GET /cursor` | 鼠标光标处的世界坐标 |
| `GET /spot` | 按「落点来源」设置自动挑一个 |

统一回一行 JSON：

```json
{"ok":1,"kind":"view","x":3555.9,"y":5871.4,"z":210.0,"water":0,"src":"view"}
```

`water=1` 表示 z 贴 0 —— 该点在水面，陆军/建筑投上去会漂在水面上。
取不到时 `{"ok":0,...,"why":"no-spawn-point [视野× 选中× 光标× ]"}`，方括号里是逐来源的诊断串。

MCP 侧对应工具 `get_spawn_point`（参数 `which` = `view` / `selection` / `cursor` / `auto`）。

### 用

| 用途 | 落点怎么定 |
|---|---|
| `POST /summon?place=view\|selection\|cursor` | 指定来源，只对下一单生效 |
| `POST /summon?x=&y=&z=` | 直接给世界坐标（给了 `x` 与 `y` 即以此为准） |
| `POST /summon`（两者都不给） | 按「落点来源」设置 |
| `POST /copy`、`/wnb`、`/crate` | 光标优先 |
| `POST /order?act=move&x=&y=&z=` | 指挥移动的目标点 |

`/summon` 回执带**实际落点**，便于调用方自查：

```
summon=1 objs=[0A1B2C3D] at=3556,5871,210 via=视野中心 ok
```

MCP 各工具的对应参数：`summon_unit` / `build_structure` / `drop_crate` 的 `place`。

## 四、单位坐标

- 字段：选中链给的是 Drawable；`body = [Drawable+0x138]`（该对象即 Thing），坐标在 `body+0x38`(x) / `+0x3c`(y) / `+0x40`(z)。
- 全图枚举：`GET /objects` 每个对象都带 `x` / `y` / `z`。
- ⚠️ 取 body 要先归一化：召唤物**自身就是 Thing**，此时 `[obj+0x138]` 为 0，
  要退到 Thing 判据 `[+0x33C]`。不归一化会让定住/血量/收编/摧毁等操作静默跳过。

## 五、已知局限

1. **没有地形吸附**。`?x=&y=&z=` 给的坐标**原样**交给 `CreateUnit`：
   z 不对就浮空或埋地；x/y 落在水面，单位就生成在水面上 —— **这就是「投到海里」的直接原因，
   跟 z 无关**。
   `CreateUnit`（VA `0x605240`）函数体内确实会调 `0x544E40`（调用点 `0x60545C`），
   但那个函数的语义**尚未实测定论**，不能指望它替调用方纠正 x/y。
2. **水面判定很粗**：只看 `z < 1.0`。地图水面高度恒为 0，够用；但没有「该点可否建造 / 可否通行」的概念。
3. **光标来源不适用于远程/无人操作**：见 §二。
4. **视野中心依赖客户区尺寸**：窗口尺寸异常（最小化为 0、未就绪）时该来源判失败，自动回退下一个来源。
5. **落点无范围校验**：只在 `|p| < 1e6` 且不贴近原点这一层过滤，不检查是否在地图内。
