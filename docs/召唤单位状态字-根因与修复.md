# 召唤/复制单位「功能失效」根因与修复

> 现象：用修改器**召唤**或**复制**出来的单位，技能是灰的、护盾/能力**不回复**；  
> 而同样一栋**正常建造**出来的建筑一切正常。  
> 本文记录完整排查过程、证据链、修复配方与补丁。



---

## 一、结论

修改器创建单位时走的是**裸 `CreateUnit`**，缺了游戏"创建后处理"这一步 ——  
对象（Thing）的 **6 个状态字**停在"半初始化"值，导致单位的**状态机接不上**：  
技能不可用、护盾回复不触发。

**把这 6 个字按"激活态"写一次，单位立刻恢复正常。**

| 偏移（相对 Thing） | +0x80 | +0x84        | +0x88 | +0x90        | +0x94        | +0xD0 |
| ------------ | ----- | ------------ | ----- | ------------ | ------------ | ----- |
| 写入值          | `0`   | `0x00000800` | `0`   | `0x00000002` | `0x00000020` | `0`   |

---

## 二、排查过程与证据链

### 1. 排除"缺模块 / 缺结构 / 缺收尾"

逐字节对比同一种单位（`AlliedAegisLargeDefenseBase`，hash `0x32535841`）的  
"建造版" vs "修改器版"：

| 比对项                          | 结果                             |
| ---------------------------- | ------------------------------ |
| Body 模块                      | 完全相同（除回指 Thing 的指针）            |
| HP 结构体（`[Thing+0x33c]`）      | **逐字节相同**（连 `+8 = -1.0f` 哨兵一致） |
| 16 个模块的 vtable 集合            | 完全相同                           |
| owner / 玩家计数器                | 相同                             |
| `[Thing+0x4db]`（曾被怀疑是"收尾标志"） | **两边都是 0** → 该假设作废             |
| 唯一实质差异                       | **就是那 6 个状态字**                 |

### 2. 自己给游戏注入 F 键，抓到状态机的真面目

用 `research/memscan/sendkey.py`（自己控制游戏：ALT 解前台锁 + SetForegroundWindow +  
keybd_event/PostMessage 双保险）在**建造单位**上按 F，实测：

|           | +0x80    | +0x84        | +0x88    | +0x90        | +0x94        | +0xD0 |
| --------- | -------- | ------------ | -------- | ------------ | ------------ | ----- |
| 静息态       | 20000000 | 00080000     | 00800000 | 0            | 00004020     | 40    |
| **按 F 后** | **0**    | **00000800** | **0**    | **00000002** | **00000020** | **0** |
| +2 秒后     | 自动翻回静息态  |              |          |              |              |       |

- 同一时刻，**召唤单位一个字都不动** → 它的状态机根本没被接通。
- "翻回静息态"就是玩家感受到的"**回盾时间很短**"。

### 3. 校准即修复

把召唤单位这 6 个字写成上表的"激活态"后：

- 技能从灰变可用；
- 用 `/health?mode=1` 把血打到 1，**血量自己回到 3000**（护盾/血量回复生效）；
- 实机确认：**复制单位与建造单位回复一致**；  
  随后对"一个复制 + 一个召唤"两个单位重复校准 → 同样恢复正常。

## 三、配套发现

### 3.1 `CreateUnit` 返回的是 **Thing**，不是 Drawable ⚠️

- 证据：`/summon` 返回的 obj vtable = `0x00C4DB60`（**Thing** 的 vtable），  
  且 `[obj+0x138]` 是浮点垃圾（约 60.0f），不是对象指针。
- 后果：`SummonByHash` 里原有的 `SetUnitState` 护栏要求  
  "`[obj+0x138]` 是有效对象指针" → **恒定不成立 → 该护栏每次都跳过 →  
  `SetUnitState`（写 `[Thing+0xBC] |= 0x80000000`、`[Thing+0xC8] |= 0x800`）从来没生效过。**
- 修复：改用 **Thing 专有的 HP 结构指针 `[obj+0x33c]`** 做判据（见补丁 `ResolveThing`）。

### 3.2 `[队伍对象+0x10]` 是**瞬态**字段，训练器却当硬性前提 ⚠️

- `SummonByHash` 一开始就读 `[team+0x10]` 当 `teamMember`，读不到就报  
  **"归属对象 +0x10 为空"** 直接失败。
- 实测：同一个队伍对象 `0x032BC6A0`（vtable 仍是 `0x00C5BCE0`），  
  这个字段**时有时无**（有单位被选中/正在被处理时非 0）→ **召唤/复制会时好时坏**。
- 建议修复：像"PlayerID 全局量保留上次有效值"那样 **缓存最近一次非 0 的 `team+0x10`**，  
  或在失败时回退到"选中单位的 owner"（现有回退分支只在 `team==0` 时走，够不着这个场景）。

## 四、补丁（`ra3-copilot/src/actions.cpp`，`SummonByHash`）

`ActCopySelected()`（复制）内部就是调 `SummonByHash(hash,1,...)`，  
所以**改一处即可同时覆盖"召唤 + 复制"**。

1. **创建后补写状态字**：对每个 created 对象 → `ResolveThing()` 求出 Thing →  
   按上表写 6 个字（走 `SafeWrite32`，自带 `IsMemOk` + SEH 护栏）。  
   日志：`[召唤] 创建后状态字补写：N 个单位 × 6 字（成功写入 M 次）`。
2. **修正 `SetUnitState` 护栏**：改用 `ResolveThing()` 判据 → 该状态位终于会真正写下去。

> 构建：`build.bat`；产物在 `build_out\ra3copilot.dll`  
> （root 的 DLL 被运行中的游戏锁住，需**退游戏**后覆盖再重注入）。

### 注意事项

- 这 6 个字是**活字段**：`+0x90/+0x94` 会被游戏**逐帧重算** ——  
  所以外部 `poke` 只能"踢通状态机"，**不是永久修复**；永久修复必须做进创建流程，即本补丁。
- 写入会被游戏部分回写（实测写后回读变成 `20000000 / 00080800 / 00800000 / 0`），  
  但**写这一次就足以让状态机接通**（之后按 F 能整组翻转并保持）。
- **验证"回盾"必须让单位真被打伤**：裸改 `HP+0x04` 不会更新"受伤簿记" `HP+0x08`  
  （未受伤时 = `-1`），技能不会响应。

## 五、HP 结构里的回复字段（`[Thing+0x33c]`，实长 ≥ 0x50）

| 偏移                    | 含义                                      |
| --------------------- | --------------------------------------- |
| +0x04 / +0x0C / +0x10 | 当前 / 上限 / 备份                            |
| +0x08                 | 当前+1；未激活/未受伤时为 `-1.0f`                  |
| +0x18 / +0x1C         | **回复窗口起/止**（时间单位 ≈125ms，窗长 16 ≈ 2 秒）    |
| +0x30                 | `0x2B`(43)                              |
| **+0x34**             | **"回复中"标志（游戏逐帧重算，poke 会被清回 0）**         |
| +0x40 / +0x48 / +0x4C | `0x42B06` / `0x98C45D5D` / `0x98C45D5D` |

## 七、裸 `CreateUnit` 不是所有类型都安全

**现象**：把**步兵类**模板（龙炎军 / 神州步兵 `0x51A8FBE1`，模板 `09D61428`）交给裸 `CreateUnit`：

```
[05:58:54.630] CreateUnit  pos=3780.0,5240.7,200.0 a1=09D61428 a2=0319C6A0
                （训练器捕获到 "CreateUnit 调用异常（参数/地址不符）"）
[05:58:54.961] [崩溃] code=C0000005 at 006FE7E3 (RA3_1.12.game)
```

即 **331 ms 后游戏崩在 `0x006FE7E3`**（DLL 日志同刻留下寄存器现场）。

**与"CreateUnit 被 stub → esp 失衡"不是同一回事**：那次崩在 `0x00ACFD17`；
而且这次 `create@00605240` 字节 = `8B 4C 24 08 83 EC 3C 53`（**真函数**，没被 stub）。

**与本文的补丁无关**：
- 崩的那次 `CreateUnit` 直接抛异常 → `made = 0` → **补丁一个字都没写**；
- 崩前若干次成功召唤（埃癸斯 / 航母 / …）都正常补写了状态字，且新召唤的埃癸斯状态字 =
  `{20000000, 00080800, 00800000, 0, 00004020, 40}` —— **与正常建造单位一致** ✅。

**系统性风险**：`unit-codes/data/callable_final.tsv` 当年**只用 `/resolve` 验过"模板存在"**，
**从没验过"能否真正创建"** → 召唤列表里可能藏着会把游戏搞坏的类型。

**建议**：
1. 召唤加**类型防护**：**步兵类默认拒绝**（训练器已有 建筑/载具/海军/空军/步兵 分类字段，可直接用）；
2. 维护"创建失败"黑名单（按 hash 记住，永不再试）；
3. 长期:把"**实测可创建**"（而非仅 `/resolve`）作为入表门槛。

### 两条踩坑铁律

1. **HTTP 接口（17832）是单线程 + 每请求 ≤256B + `select(200ms)` 超时** →  
   串行逐个 `/peek` 只有 ~0.5Hz；**要高频采样必须并发多请求**。
2. 以前记的 `0x838AB0 / 0x84A0B0 / 0x7191D0 / 0x6FC6C0 / 0x5571C0` 等  
   **全是运行时 VA**（不是 RVA），可以直接 `/read` / 反汇编。  
   （顺带否掉一条：`VA 0x5571C0` 只是赋值器 `[[0xcd8ce4]+0x50] → [ecx+0x17db0]`，  
   **不是**"把单位注册进每帧更新表"。）
