# RA3 / 日冕：单位代码是怎么实现的

> 结论：**"单位代码"就是 SAGE 引擎的「对象类型名字哈希」** —— 对单位模板名做小写化后，跑一个
> SuperFastHash 变体，得到 32 位无符号整数。它不是 CRC32、不是 FNV、也不是任何标准哈希，
> 所以之前"离线算不出来、只能查表"。
> **现在算法已逆出并 408/408 实机数据验证通过**，任意名字都能离线算代码，不再需要查表。

---

## 1. 一句话结论

```
单位代码 = StringHasher.Hash( ObjectTemplateName.lower() )
```

## 2. 算法（原样出自 WrathEd2012）

社区工具 **WrathEd2012**（SAGE 引擎的编译/反编译工具，作者 Lauren / Darth Jane，GitHub `Qibbi/WrathEd2012`）
里有 `SAGE/StringHasher.cs`，直接还原了游戏里的实现：

```csharp
public static void Hash(string value, out uint currentValue)
{
    byte[] input = Encoding.UTF8.GetBytes(value);
    int numBlocks = input.Length / 4;
    int extra = input.Length % 4;
    currentValue = (uint)input.Length;          // 种子 = 字符串长度
    int idy = 0;
    for (int idx = numBlocks; idx != 0; --idx)
    {
        currentValue += (uint)(input[idy + 1] << 8 | input[idy]);
        currentValue ^= (((uint)(input[idy + 3] << 8 | input[idy + 2])
                          ^ (currentValue << 5)) << 11);
        currentValue += currentValue >> 11;
        idy += 4;
    }
    /* 尾部 1/2/3 字节各有一支；最后 5 步雪崩混合 */
    currentValue ^= currentValue << 3;  currentValue += currentValue >> 5;
    currentValue ^= currentValue << 2;  currentValue += currentValue >> 15;
    currentValue ^= currentValue << 10;
}
```

* 这是 **Paul Hsieh 的 SuperFastHash 的一个变体**（环内两步的写法与公开版不同），全程 32 位回绕。
* **大小写敏感**：游戏/工具编译数据时**统一先小写**再算，所以 `AlliedBarracks` 与 `alliedbarracks` 结果相同。
  直接拿原始大小写去算会全错——这是最容易踩的坑。
* `0xXXXXXXXX` 这种 10 字符串会被原样当十六进制解析（工具侧约定），不是哈希。

Python 既有实现见 `tools/sage_hash.py`，命令行工具 `tools/unitcode.py`。

## 4. 游戏内部是怎么"实现单位的"

RA3 属于 SAGE 引擎（Generals / BFME / C&C3 / RA3 同源），**运行时没有 XML、也没有名字**：

```
            作者写的 XML (Mod SDK)
                    │  BinaryAssetBuilder 编译（离线）
                    ▼
   ┌──────────────────────────────────────────────┐
   │  data\static.N.manifest   结构/schema 表      │
   │  data\static.N.bin        记录数据本体         │
   │  data\static.N.relo       重定位表（指针修补）  │
   │  data\static.N.imp        导入/引用表          │
   └──────────────────────────────────────────────┘
            打包进 Data\Core*.big（按补丁号 N 逐级覆盖）
```

* 每个 ObjectTemplate 在编译期被折成一个 **32 位哈希**，文件里只存这个数；
  所以在 `mod.bin` 里**搜不到 `AlliedAirfield` / `CelestialDF41` 这种定义名**（只在被别处引用的字符串里出现）。
* 名字只保留在两类地方：
  1. `*.manifest` 的**符号表**（形如 `GameObject:AlliedAirfield`、`WeaponTemplate:xxx`），供跨资产引用解析；
  2. 本地化字符串表：`mod.str` / `gamestrings.csf` 的 `NAME:<模板名>` 键。
* 正因如此，**离线重算哈希**才是"能不能自己造对象引用"的关键 —— 这条现在通了。

### 本次实际挖出来的符号表位置

| 文件 | 内容 | 数量 |
|---|---|---|
| `Data\WBData.big` → `data\worldbuilder.manifest` | **原版对象调色板全表** | **2749 个 `GameObject:`** |
| `Data\Core13.big` → `data\mod.manifest` | 1.12/Mod 增补对象符号 | 310 个 `GameObject:` |
| `CoronaResources\Cor_ENG.big` → `data\mod.str` | 日冕字符串表 `NAME:xxx"中文"` | 915 条 NAME |
| `Data\Lang-ChineseT13.big` → `data\gamestrings.csf` | 原版中文串（键为大写 `NAME:ALLIEDBARRACKS`） | 522 条 NAME |

> 顺带解出一个格式坑：**RA3 的 CSF 字符串是「按位取反的 UTF-16LE」**（`char = ~u16`），
> 直接按 UTF-16 读出来是 `ﾤﾯﾍﾐ…` 这种半角假名乱码。解析器见 `tools/csf_read2.py`。

1. **不再需要"只能查表"**：`units_corona.h` 可以降级为"带中文名的别名表"，

   和游戏里模板表里的是否一致"。

## 8. 为什么"同一个单位有好几个代码"？

**核心：RA3 里"单位名"不等于"玩家眼里的单位"。**
玩家眼里的"凌波护卫战车"在数据里是 8 个**各自独立的 ObjectTemplate**，
它们共享同一套 `NAME:`/图标，但行为不同、代码不同。

### 8.1 两类完全不同的原因

**A 类：真·同一单位的多形态/多状态（占绝大多数）**

| 后缀 / 模式 | 含义 | 例子 |
|---|---|---|
| `_Naval` / `_Water` / `_Ground` / `_Air` | 两栖或变形单位的另一种介质形态 | `AlliedMCV_Naval`、`CelestialAntiInfantryVehicle_Water`、`CelestialMCV_Air` |
| 变形目标名（不同前缀但同中文名） | 变形后是另一个模板 | 凌波护卫战车 ↔ `CelestialWaveriderIFV_*` |
| `_Enhanced` | 协议/升级后的强化版 | `AlliedAntiAirShip_Enhanced`（水翼船） |
| `_Dropped` / `AirDrop_*` / `AirAssault` | 空投/空降形态（省掉出场动画） | `CelestialAntiInfantryVehicle_Dropped` |
| `_HeavyTransport` / `_Transport` | 搭载/运输态 | `AlliedAntiInfantryVehicle_Transport` |
| `_Veteran`（部分） | 直接以老兵级出场 | `...Projectile_Veteran` 系列 |
| `_AI` / `_NoReplace` | 给 AI 用 / 建造时占位不顶替 | `AlliedMiner_AI`、`AlliedMiner_NoReplace` |
| `ChronoBeacon_*` | 超时空传送落点形态 | `AlliedChronoBeacon_MCV` |
| `_Movie` / `S0x_*` | 战役演出/一次性脚本对象 | `JapanAntiVehicleVehicleTech3_Movie` |
| `Firework` / `_EMC` / `_2024A~D` / `_Old` | 彩蛋 / 活动 / 旧版残留 | `CelestialAntiStructureShip_Firework_2024A` |
| `WithTrailSomke` 等 | 纯挂点特效差异 | `CelestialFighterAircraft_WithRedTrailSomke` |
| `_TiberiumField` | 散矿图专用变体 | `AlliedMiner_TiberiumField` |

统计（可玩对象 732 条里）：带 `_Enhanced` 后缀 66、`_Naval` 15、`_TiberiumField` 13、`_Water` 7、`_Ground` 5、`_EMC` 5、`_NoReplace` 4；家族成员数最多 12。

**B 类：中文名撞车，其实不是同一个单位**
不同阵营的同类单位共用了一个通用中文名，例如「基地车」= `AlliedMCV` / `SovietMCV` / `JapanMCV`，
「工兵」= `AlliedEngineer` / `JapanEngineer`，「Fortress Wall」= 三家 `*WallPiece`。
分组时**必须带上阵营**，否则会把它们错并成一个单位。

### 8.2 只想留一个 → 最靠谱的判据是 `DESC:`

游戏数据里有一条非常干净的信号：**同一单位家族中，只有会出现在建造/生产面板的那个基础模板
有 `DESC:`（面板说明文字），所有形态变体都没有。**

```
DESC:CelestialAntiInfantryVehicle   → 有   ✅ 基准形态
DESC:CelestialAntiInfantryVehicle_B → 没有 ❌ 变体
DESC:CelestialFighterAircraft       → 有   ✅
DESC:..._WithRedTrailSomke          → 没有 ❌
DESC:AlliedMCV                      → 有   ✅ （_Naval / _Enhanced 都没有）
```

判定优先级：

1. 家族里**恰好一个**有 `DESC` → 留它（`unit_codes_trainer.tsv` 的 469 个家族中 462 个，98.5%，最省事）；
2. 家族里**一个都没有** → 说明整族都是变体/战役对象，留**名字最短**的那个（去掉 `_后缀` 的根）；
3. 家族里**多个有 `DESC`** → 说明是不同阵营/真不同单位共名，按阵营各留一个。

这条规则已经做进表里：`is_primary` 列 + `unit-codes/out/ra3_unit_codes.html` 的「**只看基准形态**」勾选框。
5461 条里标出基准形态，其中候选可玩对象内 472 条。

### 8.3 但注意：这里的"保留"分三种意思

| 你想做的事 | 正确做法 |
|---|---|
| **召唤菜单/列出去重** | 按上表挑 `is_primary=1`，只展示基准形态 → **推荐**，零风险 |
| **想直接召唤某个形态**（如水中形态） | 别合并，保留 `_Naval`/`_Water` 那一条；基准模板出场是"出厂形态"，要下水得自己切 |
| **想在 mod 里真的删掉那些对象** | ⚠️ **不要删定义**。SAGE 的引用是哈希，删了定义后引用它的 CommandSet / OCL / 升级 / 战役脚本**不会报错，直接崩**。社区标准做法是"**覆盖**而不是删除"——在 XML 层去掉引用或不打包对应 XML |

> 一句话：**"去重"是展示层的事，别动数据层。**

## 10. 官方单位图鉴：最权威的数据源 + "能用"的判据

### 10.1 数据从哪来

日冕官网的「单位图鉴」页面 **<https://cor-games.com/units/>** 本身不含数据，
前端 `fetch` 的是：

```
https://cor-games.com/data/game_objects/game_objects.jsonl     （约 1.7 MB / 2631 行）
```

拉取工具：`tools/fetch_official.py`（支持 `--proxy`）。它的字段比我们此前拼出来的任何来源都全：

| 字段 | 含义 |
|---|---|
| `editor_name` | **对象模板名**（就是算哈希用的那个名字） |
| `display_name` | **官方中文名**（最权威，优先于我们从字符串表猜的） |
| `side` | 阵营：`Celestial` / `ALLIES` / `SOVIET` / `JAPAN` / `Neutral` / `Civilian` |
| `editor_sorting` | 分类：`unit` / `structure` / `campaign_units` / `campaign_structures` / `system` / `misc_man_made` / `destructible_props` … |
| `kind_of` | **类型标志位列表**（`SELECTABLE` / `INFANTRY` / `VEHICLE` / `SHIP` / `AIRCRAFT` / `STRUCTURE` / `IMMOBILE` / `CRATE` / `IGNORES_SELECT_ALL` / `TRANSPORT` / `SUMMONED` …） |
| `logic_commands` | 可用指令（含 `Command_Construct*` 的就是可建造对象） |
| `button_image_name` / `select_portrait_name` | 按钮 / 头像图标名 |

### 10.2 "能召唤" ≠ "召唤出来能用"

用户实测：

```
波塞冬巡洋舰  0x9356389F  AlliedAntiNavyShipTech3       ✅ 能正常召唤出来用
              0xDB5A5941  AlliedChronoBeacon_Poseidon    ❌ 创建得出来，但不可选、不能用
```

**两个模板在运行时都能通过 `ThingFactory::Find`（= HTTP `/resolve`）**，
所以"逐条实测能不能 resolve"这条路**分不出它们**——实测只证明**模板存在**，
证明不了**创建出来的对象能不能操作**。

**判据：`kind_of` 里有没有 `SELECTABLE`。**
有 → 玩家可选中可操作；没有 → 生成出来是个"壳"。缺 `SELECTABLE` 的几类：

| 标志位 | 是什么 | 例 |
|---|---|---|
| `IGNORES_SELECT_ALL` | 超时空传送 / 空投的**抵达体** | `AlliedChronoBeacon_*`（21 个）、`SovietTeslaAirAssault*` |
| `TRANSPORT` | 运输 / 搭载体 | `CelestialAirDrop_Land` |
| `SUMMONED` + `UNATTACKABLE` | 技能召唤的临时装置 / 建筑子物件 | `AlliedPowerPlantTurbine` |
| （无标志） | 自杀 / 俯冲类特攻机 | `JapanYumiAircraft` |

据此从 441 条实测清单里剔除 **31 条**，剩 **410 条**，刷新进 `units_corona.h`。
被剔除的每一条连同原因写进 `data/callable_dropped.tsv` 留档。

判据实现：`tools/official_db.py`（`is_usable` / `reason_unusable`）；
过滤工具：`tools/filter_usable.py`；上游工具 `ra3-copilot/tools/fix_callable.py` 也已内置同一道过滤。

### 10.3 三层判据合起来才是"真正能用的单位"

| 层次 | 判据 | 能回答的问题 | 工具 |
|---|---|---|---|
| ① 名字 → 代码 | `StringHasher.Hash(name.lower())` | 这个对象代码是多少 | `sage_hash.py` |
| ② 模板是否存在 | `ThingFactory::Find` / HTTP `/resolve` | 能不能**创建**出来 | `probe_callable.py` |
| ③ 创建出来能不能用 | `kind_of` 含 `SELECTABLE` | 能不能**操作** | `official_db.py` / `filter_usable.py` |

三者缺一不可 —— 只看 ① 会拿到拼错/未启用的名字，只看 ①+② 会拿到"不可用的壳"（波塞冬就是这个坑）。
